## What Failed
- Initial Card component used React.createContext at module scope without 'use client', breaking RSC production builds on every Server Component that imports Card.
- Three pilot layouts (dad-joke-of-the-day, proper-wine-pour, slang-translator) called getTranslations server-side but never mounted NextIntlClientProvider, so client components calling useTranslations would throw at SSR.

## Patterns
- When adding context-based compound components to @repo/ui, the file must start with 'use client' — createContext is unavailable in RSC and only fails at production build, not in vitest/jsdom.
- next-intl layouts need both server-side getTranslations AND a client-side NextIntlClientProvider wrapping children; renderWithProviders in tests masks the missing provider, so a production build is the only reliable check.
- Pair every new responsive variant with a vitest test that asserts the breakpoint classes (sm:/md:) are emitted, since visual snapshots alone don't catch class-name regressions.

## Anti-Patterns
- Trusting unit tests that wrap render in a provider helper to validate that production layouts mount the same provider — the helper hides missing providers.
- Adding React.createContext to a shared UI package without 'use client' and without running a real `next build`; vitest passes because jsdom isn't RSC.
- Including review findings for issues from unrelated repos (#1011/#1012/#1013 reference docker/ paths that don't exist in lr-apps) — cross-issue review scope should be filtered before reporting.
