## What Worked
- next-intl scaffold landed cleanly with `messages/<slug>/{en,es}.json`, parity test (`__tests__/i18n-message-parity.test.ts`), and locale switcher per pilot app.
- Full test suite green: 1038 web tests + 241 ui tests passed; turbo cache hit on all 12 packages.
- Review caught and fixed two production-breaking issues before merge (missing `NextIntlClientProvider` wrappers; Card RSC crash from missing `'use client'`).

## What Failed
- Pilot layouts called `getTranslations` server-side but never mounted `NextIntlClientProvider`, so client components (`JokeViewer`, `SlangApp`, `WineApp`) would throw "No intl context found" at runtime — masked by test-only providers in `renderWithProviders`.
- `packages/ui/src/components/card.tsx` used `React.createContext` at module scope without `'use client'`, crashing `next build` in any RSC importing Card.
- Three review-listed issues (#1011/#1012/#1013) referenced a `docker/` directory that doesn't exist in this repo — wrong-repo noise, not real findings.

## Patterns
- When a server layout uses `getTranslations`, also wrap children in `NextIntlClientProvider` with `getLocale()`/`getMessages()` so descendant client components get an intl context in production.
- Any shared UI primitive that uses `createContext`/`useState`/`useEffect` must declare `'use client'` at the top of the file, or it will break every RSC that imports it.
- Message-parity tests (assert `en.json` and `es.json` have identical key sets) catch missing-translation drift cheaply.

## Anti-Patterns
- Test render helpers that silently inject providers (`NextIntlClientProvider`, theme, etc.) hide missing-provider bugs from suites that would otherwise catch them. Either render through the real layout in integration tests, or omit provider injection from unit tests.
- Trusting cross-repo issue references in a review without confirming the target paths exist in the current repo wastes triage cycles.
