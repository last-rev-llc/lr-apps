## Patterns
- Idempotent Postgres migrations: pair `create ... if not exists` with `do $$ begin ... exception when duplicate_object then null; end $$` for policies that lack an `if not exists` clause
- For tables that predate the repo, down-migrations should drop only the new objects (trigger/function/policy/indexes) and leave the table intact to avoid data loss
- App-layer permission gating (`crm:admin`) with permissive `(true)` RLS policy is the right pattern when contacts are org-shared rather than per-row owned

## Anti-Patterns
- Don't `drop table` in a down-migration when the table predates the repo — data loss risk
- Don't write per-row RLS predicates when access is gated at the app layer; a single permissive policy is clearer
