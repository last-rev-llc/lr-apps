# Internationalization (i18n)

LR Apps uses [`next-intl`](https://next-intl.dev) for internationalization. This guide covers the directory layout, locale resolution, and the day-to-day workflow for adding strings, locales, and apps.

## Status

The i18n system is rolled out as a pilot across three apps:

- `dad-joke-of-the-day`
- `slang-translator`
- `proper-wine-pour`

Each pilot has English (`en`) and Spanish (`es`) catalogs. `en` is the default locale — when a key is missing in another locale, `en` is loaded as a fallback for that catalog.

## Directory layout

```
apps/web/
├── i18n.ts                         # next-intl request config + locale loader
├── next.config.ts                  # wraps config with createNextIntlPlugin('./i18n.ts')
├── components/
│   └── locale-switcher.tsx         # client component, drops cookie + router.refresh()
└── messages/
    └── <slug>/
        ├── en.json
        └── es.json
```

Each pilot app has its own `messages/<slug>/<locale>.json`. Keys are namespaced under the slug at runtime, so consumers reference them as `useTranslations('<slug>.<group>')`.

## Locale resolution

Locale comes from the `NEXT_LOCALE` cookie. When the cookie is missing or set to an unsupported value, the default locale (`en`) is used. The `LocaleSwitcher` component sets the cookie and triggers `router.refresh()` so server components re-render with the new catalog.

Supported locales and pilot slugs are exported from `apps/web/i18n.ts`:

```ts
export const SUPPORTED_LOCALES = ["en", "es"] as const;
export const DEFAULT_LOCALE = "en";
export const I18N_PILOT_SLUGS = [
  "dad-joke-of-the-day",
  "slang-translator",
  "proper-wine-pour",
] as const;
```

## Using translations

### Server components

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("dad-joke-of-the-day.page");
  return <h1>{t("heading")}</h1>;
}
```

For metadata:

```tsx
export async function generateMetadata() {
  const t = await getTranslations("dad-joke-of-the-day.layout");
  return { title: t("title"), description: t("description") };
}
```

### Client components

```tsx
"use client";
import { useTranslations } from "next-intl";

export function MyComponent() {
  const t = useTranslations("slang-translator.dictionary");
  return <input placeholder={t("searchPlaceholder")} />;
}
```

### Interpolation

ICU-style placeholders are supported:

```json
{ "subheading": "{jokes} jokes across {categories} categories" }
```

```tsx
t("subheading", { jokes: 55, categories: 7 })
```

### Pluralization

For now we use explicit singular/plural keys (`xSingular` / `xPlural`) and pick at the call site. The full ICU `plural` syntax is supported by `next-intl` if a future use case needs it.

## Adding a string

1. Add the key to `messages/<slug>/en.json`.
2. Add the same key to every other `messages/<slug>/<locale>.json` (mirror the structure exactly).
3. Replace the literal in your component with `t('<group>.<key>')`.
4. Run `pnpm --filter @repo/web test -- i18n-message-parity` — the parity test fails the build if any locale is out of sync.

## Adding a locale

1. Add the locale code to `SUPPORTED_LOCALES` in `apps/web/i18n.ts`.
2. For each pilot slug, create `messages/<slug>/<locale>.json` with the same key set as `en.json`.
3. Add a label entry to `LOCALES` in `apps/web/components/locale-switcher.tsx`.
4. Run the parity test.

## Adding a new app to the pilot

1. Add the slug to `I18N_PILOT_SLUGS` in `apps/web/i18n.ts`.
2. Create `messages/<slug>/{en,es}.json` and populate them.
3. In the app's `layout.tsx`, mount `<LocaleSwitcher />` somewhere in the header nav.
4. Replace literals with `useTranslations` / `getTranslations` calls.

## Parity test

`apps/web/__tests__/i18n-message-parity.test.ts` flattens every catalog to dot-paths and asserts that every non-default locale has the same key set as the default locale. The test prints a clear diff when a key is missing or extra. A locale that is missing keys cannot ship — fix the JSON before merging.

## Why slug-namespaced catalogs?

The merged messages object loaded into the request context is shaped like:

```json
{
  "dad-joke-of-the-day": { ... },
  "slang-translator": { ... },
  "proper-wine-pour": { ... }
}
```

Each `useTranslations("<slug>.<group>")` call scopes to that slug's catalog without the runtime needing to know which app the request is for. The bundler still tree-shakes per-route, so unused slug catalogs do not bloat any individual app's payload more than the per-locale JSON itself.
